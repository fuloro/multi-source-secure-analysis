## 对研究材料的理解

[CCS 2023 论文扩展版](https://eprint.iacr.org/2024/141.pdf)研究诚实多数条件下的安全关系运算协议，
包括恶意安全。搜索索引中的 Protocol 4.1 描述了排序、秘密组末尾标记，
以及将代表行移至填充行之前的步骤。COUNT/SUM 不需要在按键排序之外再按数值排序。
因此，可以先研究各聚合操作共享的分组阶段，再实现单独的聚合操作。
直接获取 PDF 时返回了 403；在声称逐步复现之前，仍须核对完整算法和版本。
尤其不得自行补全缺失的 SUM 步骤后，将其归为论文中的算法。

[SECRECY，NSDI 2023](https://www.usenix.org/system/files/nsdi23-liagouris.pdf)
提供了算子组合与优化方面的背景。其附录讨论了使用有效位将选择或 JOIN 与 Group-by 组合，
性能评估则区分了排序和最终洗牌的成本。
对于本组件，应据此保留秘密共享中间表，并测量完整流水线成本；不要扩展为实现其查询优化器。

[SPU 协议文档](https://secret-flow.antgroup.com/docs/spu/en/reference/mpc_status.html)
指出，其 ABY3 实现是半诚实三方计算。
建议的基线假设至多一个计算方被攻破。计算方的独立管理很重要；
三个本地线程并不等于三个独立信任域。基于 ABY3 的改编实现不能继承 CCS 论文的恶意安全声明。

## 本地验证依据

Python 3.11.18；SPU 0.9.5；JAX/JAXLIB 0.4.34；NumPy 1.26.4。
尚未安装完整的 `secretflow` Python 包。本次未更改依赖。
当前目录不是 Git 仓库；`rg` 不可用。

已查阅 `.venv311/lib/python3.11/site-packages/spu/` 下的以下安装源码：

| 源文件 | 发现 | 对项目的影响 |
| --- | --- | --- |
| `ops/groupby/segmentation.py` | 使用 `jax.lax.sort`、相邻比较和扫描 | 可用于基线及原语可行性检查，不能证明与 CCS 协议等价 |
| `ops/groupby/aggregation.py` | 使用分段扫描；默认 `jnp.ones` 引入浮点数；提示公开组末尾输出位置存在风险 | 审查精确算术，并保持中间结果为秘密共享 |
| `ops/groupby/postprocess.py` | 明确属于明文后处理；键处理依赖唯一性和零填充假设 | 不得将其作为内部安全算子，也不能把零当作缺失值 |
| `ops/groupby/shuffle.py` | 按传入的 `secret_random_order` 排序 | 随机性的来源、碰撞及各方掌握的信息，均需在协议层明确 |
| `utils/simulation.py` | 将动态输入秘密共享给内存中的运行时，再重构返回值 | 可验证执行链路，但不能验证部署或结果公开策略 |

两个使用合成数据的 ABY3/FM64 冒烟检查已通过：

1. 公开候选键为 {1,2,3}，使用此前对话中的输入：计数为 [2,2,1]，
   求和为 [400,700,400]，两者均为 int32。
2. 内置排序式 Group-by：键为 [2,0,2,-1,0]，数值为 [10,0,-10,7,4]。
   排序后的键为 [-1,0,0,2,2]，末尾标志为 [1,0,1,0,1]，
   组末尾位置的求和输出为 [7,0,4,0,0]。输入虽为 int32，求和输出却为 float32。

复现命令：

```sh
.venv311/bin/python backend/groupby/experiments/probe_spu.py
```

此脚本有意公开合成数据的中间结果。
这些检查只验证了小规模输入的可行性，不能证明不会溢出、填充处理正确、性能达标或协议安全。

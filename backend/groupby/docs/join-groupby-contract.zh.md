# JOIN → Group-by 集成草案

用于团队讨论的提案，日期：2026-11-03。
已经确认使用 SPU，JOIN 由另一位队友负责；以下接口尚未与 JOIN 实现者达成一致。

## 首次演示

使用合成数据：A 持有标识符到类别的映射表，B 持有标识符与度量值记录。
建议首次查询先按标识符执行 JOIN，再按 A 的类别计算 COUNT(*) 和 SUM(measure)。
首个测试数据集建议让 A 的标识符唯一，允许 B 的标识符重复；
队友仍需确认所支持的 JOIN 变体。COUNT 统计匹配记录数，而不是去重标识符数。

```text
A: (id, category)       B: (id, measure)
           \             /
          SPU 计算提供方（暂定三方）
                         |
                   队友实现的 JOIN
                         |
          共享的 category、measure、valid，容量 N
                         |
                  我们实现的 Group-by
                         |
          共享的组键、计数、求和、有效位，容量 N
                         |
            按约定向 B 交付最终结果
```

这是仅交付聚合结果的流程提案。
在界面中展示两种算法，可以是展示公开的执行阶段、耗时和最终结果，
不需要公开连接后的中间表。
逐行特征交付应有单独的输出策略，不能因为要演示 JOIN 就默认允许这种交付。

## 待商定的交接事项

| 事项 | 初步约定提案 |
| --- | --- |
| 执行环境 | 使用同一个 SPU 运行时或会话、相同协议及计算域或环，以及顺序一致的计算方列表 |
| 数据载荷 | 秘密整数 `category[N]`、`measure[N]`，以及秘密比特 `valid[N]` |
| 容量 | 执行前商定公开的填充容量 N；实际匹配数量保持为秘密共享 |
| 填充 | `valid=0` 表示排除该行；类别或度量值为零仍是合法数据 |
| 匹配重数 | 每次匹配产生一行；重复匹配分别计数 |
| NULL | 首个测试采用内连接；外连接需要另行约定列空值语义 |
| 数值界限 | 选择公开容量 N 和度量值界限 B，防止累加器溢出 |
| 责任归属 | JOIN 队友提供秘密共享输出，Group-by 不经重构直接使用 |
| 结果交付 | 暂定最终接收方为 B；允许公开的具体字段和元数据仍待确认 |

暂不标准化原始份额的序列化格式。
首先在一次 SPU 执行中组合计算内核，或将数值保留在同一个共享运行时中。
两次独立的模拟器调用会重构各自的输出，不能据此证明实现了秘密共享的 JOIN → Group-by 流水线。

## 共同使用的合成验收数据

```text
A = [(101, 1), (102, 2), (103, 1)]
B = [(101, 200), (101, 300), (103, 400), (999, 50)]
```

按建议的内连接语义，有三行有效，标识符 999 不产生贡献。
容量为四的交接数据可以采用：category 为 `[1,1,1,0]`，measure 为
`[200,300,400,0]`，valid 为 `[1,1,1,0]`；JOIN 也可以输出其他行顺序。
预期 Group-by 结果只有一个有效组：类别 1，计数 3，求和 900。
其余输出行均无效，载荷清零。
这些明文值仅用于描述测试预期；最终流水线中的交接数据保持秘密共享。

还应测试无匹配、重复匹配、类别为零、负度量值，以及填充行类别与真实类别相同的情况。
JOIN 开发期间先使用这组接口测试数据，之后再通过真正组合的流水线运行测试。
